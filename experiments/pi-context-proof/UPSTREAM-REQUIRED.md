# Pi 0.85.1: stock input-ID blocker and disposable native patch (NOT activation)

Stock Pi 0.85.1 still has no trustworthy attempt-bound context identity. This directory now also contains `pi-0.85.1-native-input.patch`, an opt-in, pinned-byte **copied-package native patch**, `prepare-copied-pi.sh`, and offline + real-RPC tests. It never modifies globally installed Pi or existing sessions. See `PATCHED-FORK.md` for exact runtime scope and remaining integration gates.

`required-contract.test.mjs` is an executable **failing target contract on STOCK Pi**; it passes on the copied patch. The current copied patch advertises `pi-native-input-v1-live-only`: journal JSONL on restart is NOT an offline `CONTEXT_COMMITTED` proof because complete records can survive a failed fsync. Production requires a separately committed coordinator attestation of a live event; uncertain outcomes stay unresolved without automatic retry. Stock produces 4 expected failures without network, live session, or global package modification. Run:

```sh
PI_OFFLINE=1 node --test experiments/pi-context-proof/required-contract.test.mjs
```

## Exact missing boundaries

1. `dist/modes/rpc/rpc-mode.js` `case "prompt"` passes `command.message`, `images`, `streamingBehavior`, `source`, and `preflightResult`, **not** a unique `inputId`. `command.id` labels only an early accepted/queued ACK, never the ensuing user message or model context. The agent-comms backend currently strips `_input_id` before sending Pi RPC.
2. `dist/core/agent-session.js` `prompt()` transforms and expands text, then idle creates `{role:'user',content,timestamp}` with no input identity; `_queueSteer`/`_queueFollowUp` create the same anonymous user object. Its `message_start` removal of local pending entries uses `.indexOf(messageText)` (ambiguous for two identical prompts), not identity.
3. `node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js` emits each user message, then performs `transformContext`, `convertToLlm`, and `streamFunction`; there is **no mandatory, failure-propagating hook after assembled model context that receives an input identity**. Existing extension `input` sees text+source but no request ID, `before_agent_start` sees expanded text but no ID; `context` sees a copy of messages and `before_provider_request` sees payload but has no ID. `dist/core/extensions/runner.js` catches and swallows exceptions in those hooks, so even an extension-side fsync error cannot gate model send. A signed or unsigned marker embedded into user text is not an authoritative Pi input-ID binding.
4. `dist/core/session-manager.js` `_persist()` does not create the JSONL until the first assistant entry; subsequent `appendFileSync` calls have no `fsync`. A user input in Pi memory (or a `pi.appendEntry` made before first assistant) does not survive a crash. `get_entries` likewise reads in-memory state in a live process and is not a durability proof.

## Smallest upstream native change that could safely unblock

- Extend RPC `prompt`/`steer`/`follow_up` and SDK `PromptOptions` with **separate** validated 128-bit `inputId` (not `command.id`). Thread it through extension input transforms, skill/template expansion, **structured** steering/followUp queues, `clear_queue`, final `UserMessage.inputId`, agent events, and session entries. Enforce ID uniqueness per session and same-ID exact replay/otherwise conflict; no matching by text, time, or queue position. An input handled without LLM never emits a context receipt.
- `SessionManager.flushInputDurably()` must write header plus user entry **before the first assistant**, `fsync(file)` and `fsync(parent)` when newly created, or fsync the existing file; return actual `sessionEntryId`. Only then emit `input_committed`; queue ACK alone has no such effect. Session files containing any future tracked ID must always be created 0600 even by an earlier untracked turn; require private owned 0700 session directory, trusted ancestry, and owner-only 0600 preexisting session/journal before advertising capability or accepting a tracked input (never silently chmod-repair old 0644 files).
- Add an **awaited, fail-closed** `onContextReady`/`context_committed` internal callback after all `transformContext` handlers and `convertToLlm`, immediately before `streamFunction`. It must carry the `inputId` of the **specific user message still present in the assembled model context**, its durable `sessionEntryId`, and a request generation/digest. Persist the journal with fsync before emitting a LIVE success event; a failed journal/flush must prevent model invocation. A complete persisted JSONL record is NOT recoverable evidence of fsync success: on restart it may reserve a generation number but must never itself assert prior `CONTEXT_COMMITTED`. Only a separately committed coordinator live-event receipt can authorize recovery; absent that receipt leave uncertain rather than resend. If the claim is that the provider got the request (rather than Pi assembled its model input), the callback must move after final provider payload rewrite and await a transport acceptance hook; no early context hook proves provider receipt. Generation records must distinguish retry, compaction that drops a message, and cleared queues. Do **not** silently accept extension-hook exceptions.
- Tracked extension `input` handlers returning `handled` must fail prompt preflight and clear an unpersisted ID claim; a second identical ID must not receive a ghost acceptance ACK. See `native-contract.d.ts` for the typed API shape. The four executable contract tests must become green on a patched **disposable** Pi, followed by duplicate identical input, transformed skill/template input, queued steer/followUp + clear, first-user crash/restart, injected fsync failure, tool turn, compaction/overflow retry, and payload rewrite tests. Backend may forward its `_input_id` only **after** a capability handshake proves patched Pi; otherwise `CONTEXT_COMMITTED` remains off.

No feature in this directory is auto-discovered. Nothing here establishes `CONTEXT_COMMITTED` on stock Pi.
