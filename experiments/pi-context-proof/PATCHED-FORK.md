# Disposable Pi 0.85.1 native input-ID fork (not a live rollout)

`prepare-copied-pi.sh` verifies exact SHA-256 of 12 installed Pi/core/ai files, copies the 159 MB package into a private `/var/tmp` directory, applies `pi-0.85.1-native-input.patch` with **zero fuzz**, checks six patched JS modules, and prints `PI_PACKAGE_DIR` and `PI_CLI`. It does **not** patch the installed binary or create an autoload extension. The patch also updates the corresponding `.d.ts` files. Any upstream package change fails closed before patching.

**Native protocol, only on the copied package:** `get_state.nativeInputProofCapability` is `pi-native-input-v1-live-only` only when the persistent session directory has owner-only mode 0700, its ancestors are trusted/nonredirectable, and any existing session JSONL/journal are owner-only regular 0600 files; otherwise it is `null` (also under `--no-session`). Newly created ordinary Pi session JSONL files are 0600 even if a tracked input is added later; an unsafe preexisting session is rejected rather than chmod-repaired. `prompt`, `steer`, and `follow_up` accept an optional independent lowercase 32-hex `inputId` (the RPC `id` remains just command ACK correlation). A tracked prompt is rejected in nonpersistent/unsafe sessions; an exact replay of an already claimed ID never queues another user message, and conflicting text/options reject. An extension `input` handler returning `handled` for a tracked ID fails the command preflight and clears the unpersisted claim. An awaited agent-prompt failure *after* a provisional preflight ACK, or a throwing successful-ACK callback before the prompt, releases only the claim created by that invocation when no session input was appended and no steer/follow-up queue or pending input owns that ID. A throwing callback on an exact concurrent replay cannot erase the original invocation's claim; after append, the claim is retained because replay would be unsafe. The failed invocation never sends a second failure ACK after attempting success. Exact replay after a rejected fresh pre-append invocation is never an inert ghost ACK. Preflight ACKs for concurrent prompts can still be provisional; they are not delivery or context authority. Extension input transforms and prompt-template expansion keep the ID as structured user-message metadata. Queued steering/followUp and `clear_queue` use identity rather than comparing identical text. For tracked direct `steer`/`followUp` and streaming-prompt queues, Pi constructs the user message before a core enqueue; the core queue must own the exact message identity before any fallible `queue_update` observer is notified. A throwing subscriber after core enqueue may reject the SDK call or prompt preflight, but exact replay is inert only because the original core input is actually queued; `clear_queue` can remove that core identity and release an uncommitted claim. If metadata construction or core enqueue fails before either queue owns a fresh ID, only its creator may release it; an uncertain post-enqueue error never authorizes automatic replay. At dequeue, tracked-user `queue_update` and `message_start`/`message_end` are presentation notifications: each SDK subscriber is called, but one throwing subscriber cannot abort delivery after core consumed the queue identity or prevent later subscribers seeing the event. This containment does **not** apply to extension handlers, untracked turns, durable append/fsync, the native context hook, or proof-journal fsync: those remain failure-propagating and cannot manufacture a live receipt. Extensions remain disabled in the supervised adapter; arbitrary throwing extension behavior is not an approved recovery path. Before any tracked user append, its ID must already have a native claim with a valid 64-hex request digest equal to the message digest; the pre-provider context hook independently rechecks that claim against both the stored user entry and the assembled LLM message. Calling the public agent-core `prompt` directly with a self-attached `inputId` does not mint a claim, durable native user entry, live receipt, or provider opportunity. A delivered tracked user entry is flushed with fsync on session file and newly created parent, then `input_committed` emits its actual `sessionEntryId`. A native awaited, failure-propagating hook *after* `transformContext` and `convertToLlm`, *before* `streamFunction`, checks that each visible ID binds exactly one stored user entry and that a newly delivered tracked ID survived context transformations. It fsyncs `{schema,sessionId,inputId,sessionEntryId,requestGeneration,llmContextDigest}` rows to a 0600 sibling `*.input-proof` journal **and fsyncs its parent directory on every generation**, including when the proof file already exists, before emitting `context_committed`. A failed first directory fsync can leave a visible file; only a successful directory fsync on a later *explicit* turn permits that later generation's receipt/provider call. Exact replay of the uncertain first input never automatically retries it. First-user session files are durable even before any assistant entry; untracked Pi autosave timing stays unchanged while new session file/directory permissions are tightened. If flush/hook/journal fails, the model call is blocked and no context receipt is emitted.

**Attempt-bounded automatic retry on the copied fork:** During a tracked user turn, Pi passes `maxRetries: 0` into its SDK stream function, overriding configured provider retries; the Bedrock transport additionally sets AWS SDK `maxAttempts: 1` when given that zero budget. A retryable error or uncertain/truncated `length` response ends the tracked turn without Pi auto-retry, overflow compaction retry, or queued `agent_end` continuation. A successful final `stop` can still process a separately queued input, with the next user message selecting its own tracked or untracked retry budget. Exact replay does not retry a failed attempt. This is *not* a guarantee against independent retry behavior inside arbitrary custom stream functions, unreviewed provider transports, or remote/proxy infrastructure; each provider path requires its own evidence before paid use. No credentials or network calls were used for these regressions.

**What a LIVE emitted receipt establishes:** Pi assembled the specified input ID in its transformed and converted LLM context for one request generation, and both user entry and local proof were fsynced **before** calling the provider stream function. `pi-native-input-v1-live-only` DOES NOT authorize reading an old journal row as a recovered context receipt: a complete newline-terminated row can survive a failed file or parent-directory fsync, with zero emitted `context_committed` events and zero provider calls for that failed generation. Reopen parses old rows only to reserve generation numbers and reject structural corruption; it never re-emits prior context receipts. After a process crash, only a separately committed coordinator receipt attesting a LIVE emitted event can establish that prior attempt's context; absent such a receipt, outcome is uncertain and must not retry automatically. This is **not** provider transport acceptance, final provider-payload rewrite evidence, a successful model response, an assistant reply, or a coordinator acceptance receipt. `input_committed` is not `context_committed`. A signed text marker, command ACK, `get_entries`, or same text/order still is not proof. The trusted backend must negotiate this exact capability and validate the local session/proof evidence before mapping it to any coordinator `CONTEXT_COMMITTED` state; stock Pi must stay off.

**Independent product gates not resolved by this fork:** no production root marker/old-writer cutover, Stage3→4 N/K atomically accepted cohort verifier, owner-authenticated runtime wiring, per-recipient model outcome, recovery from missing coordinator live-event receipt, independent provider/proxy retries, live gateway/Toad, upstream source-TS parity, review of the compiled-JS patch or its same-UID session-file principal. Provider-specific `onPayload` hooks can rewrite/drop content after the native hook, so *do not claim provider received this exact input* without a second awaited fail-closed post-payload/transport callback. A 0600 journal under the same UID is not a human/thread authentication boundary. Malformed or truncated proof journals fail closed on resume and require explicit repair, not silent truncation.
