## Bounds to retain or classify separately

- A12 `STOP_GRACE_SECONDS=2` is process retirement grace, not summary work capacity. Linux pidfd, birth-identity checks, process-group/namespace containment, finite caller deadlines, and cancellation joins stay. A12 `BoundedRun.session/run` requires positive finite time; `run_inherited` requires a future finite absolute deadline. No model/history/count maximum is imposed there.
- Asyncio reader `limit=65536` is buffering/backpressure; PiRpcChannel explicitly assembles records through LimitOverrunError. Do not mislabel it as a64KiB history ceiling. Explicit `max_bytes` is a separate record admission limit.
- PiHelper4KiB stdout is a small typed witness/settings envelope, not session content. It deserves an encoded-envelope check (long JSON-escaped paths can grow it), but is lower priority than history/model caps; source scanning must be streamed/resource-budgeted independently.
- The10,000,000 reserve/keep-recent token checks remain duplicated in selected JS settings and Python PiCompactionSettings (base: Pi summary payloads; latest: owner_compaction_settings.py). They are a distant semantic ceiling, not a current312k-session explanation. Validate effective settings against the selected model/native settings owner instead of a separate arbitrary maximum. CompactionPolicy declarations also cap configurable concurrency8 and summaryMaxTokens32768: these are visible policy choices rather than hidden transport guards; any relaxation should stay in that owner and respect model/resource capacity.
- Native safe-integer counters/finite nonnegative costs, exact operation IDs, schema validation, malformed-record refusal, and per-path validity are representation/integrity constraints. Keep them. Existing4096 path ceiling should belong to the path/resource declaration, not be multiplied into a second independently maintained metadata schema.
- Journal64KiB intent/source/outcome envelopes (`compaction_journal.py:336,492,898`) presently hold source identities/digests/receipts, not the full summary/file list. Do not report them as the601-path failure without proving growth of those fields. Retain explicitly typed envelopes; verify any new payload references do not move whole history into them.
- Journal pending-publication LIMIT32 is a page size. Ensure callers drain subsequent pages; it is not automatically a permanent32-history cap.
- Manual compaction MAX_OUTPUT256KiB (`manual_compaction.py:478`) totals unrelated events until one correlated reply, not one record. This is another candidate for a per-record bound plus bounded work/idle deadline, rather than a total event-history quota.
- Base15a4d00 `selected_source_snapshot.py` had16MiB file/1MiB context/256KiB history limits. That module is deleted in latest parent. Do not reintroduce its caps or restore it as a workaround; audit any still-installed use separately from the selected-owner path in this incident.

## Systemic landing requirement

Use the **existing CompactionPolicy** for model/chunk work and existing transport/session owners for inactivity, framing and memory; do not introduce another policy class/list/table. It already owns concurrency, source/input ratios, summaryMaxTokens, summaryOutputRatio, inputBytes(model,reserveTokens), and summaryTokens(...). Keep provider/model identity and replay authority outside user-tunable policy. Per-message model limits remain at the native request owner; history/metadata live with native session/resource owners; byte transport/resource budgets must be consistent with the admitted plan.

Audit and change the complete chain together: prepare → selected request → every map/reduce response → Python summary decode → file metadata digest → journal intent → inherited-FD commit helper → native append/reconcile → reopen → original input admission. One serializable admission result from existing owners should cross these boundaries, rather than each consumer inventing its own constants.

Acceptance must include parent's retained session through **commit and reopen**,601+ paths, >64KiB metadata, enough individually valid chunks to exceed256KiB cumulative output, slow-but-progressing multiwave work beyond90s, and growing history beyond256MiB. Use synthetic/loopback model streams and bounded resource measurements; no paid providers are required. Verify no truncation, no dropped paths, no replay of UNKNOWN and cancellation actually reaps children. The retained-session601/211 commit/reopen case is now verified above; the other growth scenarios are proposed acceptance checks, not tests run by this audit. Also exercise more than1024 lifetime operations without losing no-replay authority.

This previous16→128MiB increase is precisely the repeated-ceiling pattern to retire. S10/Pascal owns tracked-input proof/replay semantics; S9 owns native session loading. The startup method also retains tracked user entry objects from getEntries, so merely streaming the journal file does not close its memory usage.

Current native SessionManager strict loader acReadStrictSession performs readFileSync → UTF-8 string → split lines → all JSON objects. _loadEntries stores all objects in fileEntries, _buildIndex adds them to byId, and getBranch builds every historical ancestor before prepareCompaction trims summarized history. Reconciliation does another full read. Streaming just the first read retains all of these downstream allocations.

This is a per-record traversal behavior, not a whole-history ceiling; it must not become an authority reader that silently treats an oversized record as absent. S10 owns this transcript boundary. forward/reverse have different behavior, so do not claim a universal256KiB native message limit.
