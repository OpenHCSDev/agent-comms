## 2. Recurring failure families

### A. One budget is measured many different ways (12 commits)
**Commits:** 51bbb958b, d1f7098ad, 6a14e1445, 5c5792c95, 595ec3927, 23284c8f3, 6c24cb66d, 0a0025b21, 92d246c11, 5671a4659, 266035fbc. The local refusal in 266035fbc came from the adapter's budget after compaction had already accepted the context. Before this range, the same issue was fixed in 1f6bc3895 and c9777c268.

**Why it keeps recurring:** "How many tokens will this request be" has no single answer. All of these coexist at main HEAD:
- `stack/native-session-storage.patch:1858` uses Pi's `estimateContextTokens` for `tokensBefore`.
- `:1883` sums per-message `estimateTokens` for the keep-recent limit, while `:1880` uses `policy.retainedFits` (ContextBudget) in the same loop.
- `:2061` uses `estimateTokens(currentInput) > budget`.
- `:2283` is the usage-based `getContextUsage`.
- `stack/native-context-budget.mjs:14-20`: ContextBudget switches between `estimateContextTokens(context)` and `estimateSerializedRequestTokens(serialized wire input)`.
- `stack/native-generation-policy.patch` has 10 `new ContextBudget(...)` sites, each with its own per-provider wire projection.
- `stack/native-compaction-source.mjs:38,54` uses `estimateTextTokens` for map chunks.
- `native-context-budget.mjs:132-168` falls back to regex-parsing the provider's 400 text and retrying.
- Two message converters: `native-session-context.mjs:29` vs `:44`.
- A test-only preparation path without system prompt or tools: `src/agent_comms/_pi_helpers/prepare_compaction.mjs:13` together with `native-session-context.mjs:34`. `prepare_native_source` (`owner_compaction_prepare.py:168`) is now called only from `tests/selected_summary_recovery_installed_journey.py` (TIME-6).

Each fix aligned two of these measures and left the rest.

### B. Change checks broader than the question, so compactions cancel themselves (5 commits)
**Commits:** 854f4c693/b65626e73, a29d458ec, 42c8749cd, c11451901, 41adf8b6c.

**Why it keeps recurring:** the check before and after the summary compares an entire captured record with `!=` (`compaction_source.py:44-51`). That record still includes:
- `input_revision`: a digest of all of the owner's input rows (`compaction_boundary.py:195`).
- `settings_revision`: stat, mtime, ctime and digest of up to five settings and model files (`compaction_boundary.py:124-135,140-158`).
- All retained task facts.

The second check runs after a summary that is paid for and takes minutes. Any unrelated write to these during that time throws the result away. Each fix removed one field from the comparison: Thread progress, `summary_phase`, `bus_revision`, the leaf after commit. The pattern itself (IDEN-7) is still in place.

### C. Core and Pi each hold their own copy of session and compaction state (≈8 commits)
**Commits:** 45258b835, be1a0c47f, b09638fc7, aff7f27f8, 6a14e1445, 23284c8f3, 459adb65b/588793e74, 24aa16fb2.

**Why it keeps recurring:** one compaction is split across three processes and four records:
1. The summary is produced inside the Pi child.
2. It is recorded in Core's SQLite journal: three tables, with 6 operation states, about 10 summary states and 2 publication states (`compaction_states.py:45,103,312,356`).
3. It is written to the session file by a separate node process (`native_compaction_writer.py:32`, `stack/native-compaction-commit-child.mjs`), while the live Pi child holds the same file in memory.
4. The Pi child is then told to reload (`owner_compaction_runtime.py:182-224`).

Pi's own compaction engine still exists. The env var `AGENT_COMMS_NATIVE_CONFIG_DIR`, a config-directory path, doubles as the "managed by Core" switch that turns it off. It is checked at `patch-native-adaptive-settings.py:39,43,47,57,64` and `native-session-context.mjs:73-75` (IDEN-1). Core also copies Pi's config file locations (`owner_launch.py:61-69,109-115`, TIME-7).

Every disagreement between these copies needs its own reconcile step: the UNKNOWN outcome, `reloadCompactionCommit`, and settings-revision fencing.

### D. In-flight or failed records nobody settles, which block input indefinitely (7 commits)
**Commits:** 01b11c032, d544a7164, 9555cc249, 44e6ee2c1, 266035fbc with 73a914056, 24aa16fb2, and 8d2226242 → 41adf8b6c → 18da06e36.

**Why it keeps recurring:**
- The success path and the failure path each have to remember to write or settle every record.
- Recovery logic was copied (manual vs automatic retirement; the `continued_private_session.py` copy of the unsettled rule).
- Each path that sends input (ACP, scheduled, triage, full) had to be wired into the compaction check one at a time.

Today the compaction check refuses whenever any input lacks a recorded context (`compaction_private_inputs.py:120-127` → `continued_private_session.py:82-97`). So one missed write on any failure path stops the whole inbox.

### E. Error wrappers and fallbacks that hide the cause (≥10 sites; one caused a multi-day outage)
**The outage.** `compaction_private_inputs.py:125-127` folds nine different `ValueError` reasons plus `OSError`, `sqlite3.Error` and `RuntimeError` into one message, "Selected source requires reviewed raw-history coverage floor". That hid the 266035fbc cause from 10-06 to 10-10. Branch commit 266035fbc only renamed the message; on branch HEAD (lines 129-131) a lock or I/O failure still reads as a coverage gap.

**Other sites on main:**
- `compaction_send_admission.py:34` (any journal error means "busy")
- `compaction_records.py:296`
- `cursor_publication.py:74,109,153`
- `compaction_publication.py:48-50`
- `owner_launch.py:106` (`auth_revision` returns `(0, 0)`)
- `manual_compaction_bridge.py:87-88`
- The offline budget fallback at `native-session-context.mjs:34`
- The bounded-prompt fallback added in 7e199fa23

Branch commit 78731e190 removes the `compaction_records`, `send_admission` and `cursor_publication` cases. It is not on main yet.

### F. Blocking I/O and lock contention (5 commits)
**Commits:** ab8fef139, 9d42ff50e, 361c1c1e6, 05c35409e, 44e6ee2c1.

**Pattern:** retry loops stand in for ownership.
- 59649992a moved a sleep-and-retry loop into `StoreLockContention(2.0)`.
- `owner_compaction_runtime.py:209-215` polls every 10 ms and swallows cancellation.

Cost, measured in 9875aaddb's message: a cold reply took 130 s, of which 117 s was context preparation (109 s in map plus synthesis calls).

## 4. Top five conclusions

1. **The token budget has no single owner.** At least eight estimators, two message converters and a provider-error regex retry each answer "will this fit" (family A; `native-session-storage.patch:1858,1880,1883,2061,2283`; `native-context-budget.mjs:14-20,132-168`; `native-session-context.mjs:29,34,44`). Every budget fix (12 commits) aligned two of them. The result: compaction accepts a context, and then Pi's adapter or the provider refuses it, as in 266035fbc.

2. **Compaction is one operation spread across three processes and four records:** the Pi child, the Core journal's three tables, a separate commit-writer process, and the session file. Most of the code exists to reconcile these copies: the UNKNOWN states, reload after an external write, settings-file fencing, the env-var switch that turns off Pi's own compactor (family C; `owner_compaction_runtime.py:182-224`, `native_compaction_writer.py:32`, `patch-native-adaptive-settings.py:39-64`, `compaction_states.py:45-312`). Three reload mechanisms in two days (45258b835, be1a0c47f) show the design fighting itself.

3. **The before-and-after check compares the whole world.** That makes compaction cancel itself after the provider has already been paid (family B). The fixes removed one field at a time: 854f4c693, a29d458ec, 42c8749cd, c11451901. `CompactionSource.require_current` still compares every input row's digest and settings-file mtime/ctime (`compaction_source.py:44-51`, `compaction_boundary.py:135,140-158,195`).

4. **Compaction requires perfect history records but hides why a record is missing.** Every failure path that skips a write, and every error wrapper, becomes a permanent inbox stop with a misleading message (families D and E). Main still has the wrapper at `compaction_private_inputs.py:125-127`. The 10-06 to 10-10 outage (5671a4659 evidence, then 266035fbc and 73a914056) is the clearest case. It needed a repair command for rows already corrupted.

5. **Effort went into ceremony, not removal.** 62 of 277 commits are docs or evidence only, with 510k evidence lines. Commits were duplicated (854f4c693/b65626e73) and reverted then reapplied (52c0db494/c767e319e). Pi is patched by about 5,000 lines of string-anchored patches, with 48 hash re-pins in the range. Vocabulary churn ("original", "custody", "carry") hides what each commit does. Meanwhile the duplicated owners in conclusions 1 to 3 were never consolidated. Clean forms to apply: IDEN-7, IDEN-1, TIME-7 and IMPL-12, plus AGENT-2 and AGENT-7 as the behaviours producing the debt.
