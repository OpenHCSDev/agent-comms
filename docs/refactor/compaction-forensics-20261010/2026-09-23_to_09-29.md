### A. Two or more compaction engines, each with its own trigger (about 14 bugs)

**Representative commits:** 83534c222, feab13f46, 1026a47b5, 3da0530ee, 5c8d9641a, 74e157e11, f6bff1236, 68926637b, 224cf66e5, c093d3bb6.

**Still present at HEAD:**

### B. Context size measured in different ways in different places (about 12 bugs)

**Representative commits:** 7dedd0cb0, e8d49691a, 1af49fe8a, 9e015800c, 436b600cd, febb25643, 75c8364df, 2b3a43c65, c9777c268, 3d2cac9b6, 224cf66e5, 1f6bc3895 (fixed twice).

**Units used across these places:** characters, then UTF-8 bytes, then JSON bytes, then tokens, then stale provider usage, then a Python-supplied `contextTokens`. The ratios changed from 0.55/0.35 to 0.5/0.3 to 0.7/0.2 and then into a policy object.

**HEAD evidence:**
- patch-native-auto-compaction.py:26-29 picks between two estimators.
- native-context-budget.mjs:31-33 has another `compactionRequired`.
- native-session-context.mjs:49-52 makes yet another `compactionRequired`.
- owner_compaction_settings.py:19-31 is a Python copy of Pi's settings.
- inspect-native-compaction-plan.mjs:12-13 hard-codes 272000 / 16384 / 20000. This is the catalog's own TIME-7 example.

**Why it keeps happening:**
- The context-size fact is computed in Pi, in Pi patches, in wrapper scripts and in Python.
- The wrapper adds its own limits on top of Pi's: calls 4, 1 MiB, 256 KiB, 90 s, 256 files, 1024.
- Each of those limits was later found to break real sessions and was deleted.

Patterns: TIME-7, TIME-8, IDEN-3, IDEN-5.

### C. Core writes Pi's session from outside, then reloads Pi (about 8 bugs)

**Representative commits:** 9ba0ea144, dff13a8a7, 872fb075f, 06dc706e7, 26e839343, 7e0ef0bd7, eedf7993e, 2755c2319.

**How it works:**
1. The cut point is prepared in a separate Python-spawned process: `_pi_helpers/prepare_compaction.mjs:13`.
2. It is prepared again in the running Pi process: `native-compaction-selected-summary.mjs:69` and `:214`.
3. The two results are matched by a "witness" (`firstKeptEntryId`, `revision`).
4. Python then writes the row through a separate commit child while the running Pi process is held: `owner_compaction_runtime.py:182` `persistent.external_write` and `:222` `retained.reload`.

**What this caused:**
- Pi's row fields (file operations, usage) were lost: 872fb075f.
- The row shape had to be checked by hand three times, in commit-child, the metadata patch and Python (06dc706e7).
- Cancellation had to be fought three times. The current answer is a sleep-polling loop at owner_compaction_runtime.py:212-216.

**Why it keeps happening:** the session file has two writers and two in-memory copies.

Patterns: IDEN-5, TIME-8, BOUND-3, MEMB-5, BOUND-5 (Pi JavaScript embedded in Python strings, e.g. `_SUMMARIZE` in the deleted owner_compaction_provider.py).

### D. Leftover in-flight rows that block everything afterwards (about 6 bugs)

## 4. Top 5 conclusions

**1. Compaction has never had one owner. Pi and Core each run it, with their own trigger.**
- Core never replaced Pi's in-process threshold compaction (patch-native-auto-compaction.py:16-52). Instead it added its own selected/owner engine (owner_compaction_adaptive.py, native-compaction-selected-summary.mjs) and chooses between them with an environment variable (native-session-context.mjs:73, patch-native-adaptive-settings.py:57).
- The trigger also depends on a flag our own steering patch flips (`_nativeRunHadTrackedInput`, 5c8d9641a; still at HEAD).
- Commits caused by this split: 83534c222, feab13f46/1026a47b5, 3da0530ee, 74e157e11, f6bff1236, 68926637b, 224cf66e5, c093d3bb6.

**2. Context size is computed in many places in different units, and the wrapper keeps inventing its own limits.**
- About 12 fixes in 6 days rewrote ratios, units or limits: 7dedd0cb0, e8d49691a, 1af49fe8a, 9e015800c, febb25643, d394b208c, 75c8364df, 2b3a43c65, c9777c268, 1f6bc3895.
- The "stale usage after compaction" bug was fixed on 09-25 (436b600cd) and came back on 09-28 (224cf66e5) and 09-29 (1f6bc3895). The 09-29 case was introduced by c9777c268 the day before.
