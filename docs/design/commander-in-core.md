# Commander in Core: orders and their story, native to Comms

Design for moving the commander's order book and its public record out of the scratch scripts
(`/home/ts/.cache/agent-scratch/rts/{order,judge,tool_watch}.py`) into Comms Core, so any
harness (Toad/Pi, Codex, OpenCode, Claude Code) runs a commander thread through Core's declared
tools, and every unit can read the record about it.

This design describes what `main` ships. The remaining work and its order are owned by
[`plans/commander-native-plan.md`](../../plans/commander-native-plan.md); the section
"Not built yet" below only points into it.

## What the scripts do today

| Fact | Where it lives today | Problem |
|---|---|---|
| Problems | `problems.json`, `closed.jsonl` | Second problem list beside Core's Todo store |
| Orders: deadline, check, assignee | `deadlines.json` | Second order list beside the Goal |
| Order text and send-backs | `sent.jsonl` (copy of each sent body), the bus | Copied text; replies are not linked to the order |
| What a unit did | `edits.jsonl`, written by `tool_watch.py` from Pi session files only | Copies transcript content; guesses argument spellings; blind to CLI-bridge units |
| Verdicts on edits | `verdicts.jsonl` | Only the commander's session can read or write them |
| Strikes | `strikes.jsonl` | Same |
| Public story | `docs/agents/fleet-narrative.md`, appended by `order.py strike` | A second copy of the strikes, frozen at write time |
| Board | `docs/agents/fleet-board.md`, regenerated by `order.py board` | Derived, but from the scratch stores |
| Dangling branches | `branches-agent-comms.txt`, written by hand | Not derived, not queryable |

## Lessons from running the scripts (claude-code, 2026-10-16)

The Core version must not repeat these:

1. **A done check runs on the delivered commit, not on some checkout's HEAD.** `order.py done`
   refuses unless a checkout's HEAD equals the sha, so merged work cannot be closed once the
   unit's worktree moved on, and work merged into a non-main base (P55 via #1011 into #1007's
   branch) cannot be closed at all. Core's `OrderDelivery` family (below) runs the check on the
   delivered commit or operation instead. Deriving where the commit landed (main, another
   branch, not merged) is still owed; see "Not built yet".
2. **Plain words must not flag names it quotes.** "lifecycle" inside `toad-close-lifecycle` is a
   thread name, not prose. `PlainText` treats a word joined to its neighbours by `-`, `_`, `/`,
   `.` or `:` as an identifier, and skips quoted and backticked spans.
3. **Firing moves every open order at once.** At the strike limit, one operation lists all the
   unit's open orders and transfers or releases each with the same stated reason; nobody does
   it by hand order by order.
4. **Owners include agents outside Toad.** A Claude Code agent (claude-p60, claude-ui, ...)
   takes orders by registering a thread (`agent-comms register --name NAME`), which has the
   ordinary agent role, so it can hold a Goal. No second owner kind is added.
5. **One order may carry several problems.** Orders batch related problems for one owner;
   `ProblemGoalOrder` groups every Todo assignment of a unit under its one Goal.

## What Core owns today

Every tool below is a `ToolRequest` in `src/agent_comms/tools.py`; `agent-comms tools` lists it and
`agent-comms invoke --tool NAME --arguments JSON` calls it.

### Orders and problems

| Tool | Declared | Does |
|---|---|---|
| `comms_todo_create` | `CommsTodoCreateTool`, tools.py:757 | Create a problem with its owner, checked order and deadline in one command |
| `comms_order` | `CommsOrderTool`, tools.py:745 | Reserve a Todo assignment and publish its Goal with a deadline; does not replay input |
| `comms_todo` | `CommsTodoTool`, tools.py:723 | Apply an exact revision-checked Todo command; only its commander may invoke it |
| `comms_todo_list` | `CommsTodoListTool`, tools.py:735 | Read the commander's canonical Todo orders, deadlines, strikes and hunts |
| `comms_order_done` | `CommsOrderDoneTool`, tools.py:764 | Verify the order's check on its clean delivered commit before completing its Goal |
| `comms_order_check` | `CommsOrderCheckTool`, tools.py:782 | Replace the check of an open order, recording the old check, the new one and why |
| `comms_problem_close` | `CommsProblemCloseTool`, tools.py:800 | Record installed application evidence and close only a problem with no open order |

| `comms_work_branches` | `CommsWorkBranchesTool`, tools.py:842 | Branches with commits not on main, newest first, with their open PR or linked issue and the threads that have them checked out |

### The records behind them

- **Problem = `Todo`** (`src/agent_comms/todos.py`), changed only through the `TodoOperation`
  family (todos.py:549), each member revision-checked:
  `AssignTodo` (todos.py:564), `StrikeTodo` (todos.py:586), `VoidStrikeTodo` (todos.py:602,
  the strike stays on the record), `CorrectCheckTodo` (todos.py:620), `RecordFirstCallTodo`
  (todos.py:638), `RecordHuntTodo` (todos.py:650), `DeliverTodo` (todos.py:663), `InstallTodo`
  (todos.py:679, refuses without a retained installed artifact) and `ChangeTodoState` (todos.py:695).
- **Delivery = the `OrderDelivery` family** (todos.py:34): `RecordedCommitDelivery` (todos.py:57),
  `CommitDelivery` (todos.py:81) and `OperationDelivery` (todos.py:107). The order's check runs
  on the delivered commit or operation, not on a checkout's HEAD.
- **Strike reason = `StrikeReason`** (todos.py:200), a `PlainText` that refuses fewer than ten
  words; `StrikeTodo` records it on the problem.
- **Two-owner rule = `Assignment.require_trace`** (todos.py:479): moving a problem that has had
  two or more owners refuses without the commander's traced `PATH:LINE`, which must exist.
- **Order = the problem Goal, `ProblemGoalOrder`** (goals.py:319): a unit's one Goal groups its
  Todo assignments; it is completed per problem through its checked delivery, never directly.
- **Order history = `GoalHistoryEntry`**: every transition with the Goal before and after,
  read through `comms_goal_history`.

## Work location (HARD RULE, Tristan 2026-10-16)

A problem being worked on has its work on main, or on a branch with a linked PR or issue; never on
a branch with neither. `comms_work_branches` derives the violations on read; nothing stores them.

## Rules this design keeps

- Every fact has one owner; the story, the board, overdue and dangling branches are computed on
  read. Messages are referenced, never copied.
- Constant cost: reads go through indexed rows keyed by goal or unit; nothing scans the bus.
- No env vars, no compatibility readers; FieldCodec is the one codec.
